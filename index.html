The Project

Main Goal

G.U.A.R.D.I.A.N. aims to build a secure, edge-AI driver monitoring and fleet management system for Bangladesh Transportation. The system is designed to identify observable risky driver states and behavior in real time, relate them to vehicle motion, support timely intervention, minimize continuous raw-video transmission, and securely synchronize relevant metadata.

Behind the Data Collection

These are the people who spend hours behind the wheel, carrying hundreds of passengers through Bangladesh's roads. GUARDIAN needs to be built around their real working conditions rather than around assumptions made from a laboratory.
System Design

System Architecture

G.U.A.R.D.I.A.N. combines driver-facing computer vision, vehicle movement, and road-speed context to identify potential safety risks, issue timely warnings, and record relevant events. The core monitoring and warning path is designed to operate locally.

01 / Multimodal Risk Assessment

System Overview
01

Facial Monitoring

Face landmarks, eye closure, blink patterns, yawning, and validated fatigue-related indicators.

02

Body & Pose

Head and torso movement, posture changes, and unusual movement patterns over time.

03

GPS & Road Context

Position, GPS-derived speed, road-segment matching, and verified road-specific speed limits.

04

Vehicle Motion

Vehicle speed, acceleration, and optional telemetry from compatible vehicle interfaces.

↓
Local Processing Layer

Risk Assessment Engine

Evaluates signals over time, checks data quality, applies configurable safety rules, and combines relevant evidence without treating a single noisy measurement as a confirmed risk.

Temporal Analysis Threshold Checks Sensor Validation Risk-Level Logic
↓
Output A

Driver Alert System

Audible, spoken, or visual warnings for detected fatigue indicators and sustained overspeed events.

Output B

Event Logging & Fleet Data

Timestamped events, risk indicators, and relevant metadata for later review and authorized fleet monitoring.

Design principle: basic driver alerts should not depend on an active internet connection. Cloud synchronization is a separate function. Automated vehicle control is outside the current warning-only prototype and would require additional safety validation.

02 / Camera Input & Interface

Computer Vision Pipeline

The camera interface captures and validates video frames before forwarding them to the computer-vision pipeline. Keeping camera handling separate allows compatible camera hardware to be replaced without redesigning the core face and pose processing logic.

01

Camera Source

Standard RGB webcam for the current prototype. Compatible low-light or infrared cameras may be evaluated in a later deployment stage.

02

Frame Capture

Open the camera device and capture video frames using OpenCV. Configure the device index, resolution, and frame rate.

03

Frame Validation

Check whether frames are available and usable. Handle camera disconnection, invalid frames, and insufficient visual information.

04

Vision Pipeline

Convert frames to the required image format and pass them to the Face Landmarker and Pose Landmarker for feature extraction and subsequent risk assessment.

Monitoring availability: If the camera fails or the driver's face or body cannot be detected reliably, flag the visual monitoring state as unavailable and log the event. Missing or unreliable visual data must not be interpreted as evidence that the driver is safe.
Hardware flexibility: Camera replacement may require adjustments to device configuration, frame capture, image conversion, or low-light handling. The vision pipeline can remain unchanged when the replacement provides compatible input, but detection performance must be tested again.

03 / How the Speed Alert Works

Decision Workflow

GPS identifies the vehicle's position and estimates its speed. The system matches the position to a road segment, retrieves a verified speed limit, and checks whether excess speed persists before triggering an alert.

1

Read GPS & Speed Data

Collect timestamp, latitude, longitude, GPS-derived speed, and available accuracy information.

↓
2

Validate the Measurement

Check whether the GPS data is recent and reliable. If available, compare it with a compatible vehicle speed reading and flag significant disagreement.

↓
3

Identify the Road Segment

Match the position to a road and retrieve the verified speed limit for the relevant vehicle class. Do not assume an unverified map value is authoritative.

↓
Step 4 / Calculate Excess Speed
Excess Speed = Measured Speed − Road Speed Limit

Both speeds must use the same unit, such as km/h.

↓
Step 5 / Decision Gate

Is the Excess Speed Above the Configured Margin?

Check measurement validity, the configured margin, and whether the condition persists for the required duration.

Yes + Sustained

Trigger Speed Warning

Play an appropriate audible or spoken warning, record the event, and avoid repeatedly playing the same alert every processing cycle.

No

Continue Monitoring

Continue reading measurements and checking the road segment. Clear an existing warning only after the configured recovery condition is met.

Invalid or uncertain data? Do not issue a road-limit-based warning using a guessed speed limit. Mark the result as unavailable, record the data-quality issue, and continue monitoring when reliable readings return.
Calibration note: a 5–8 km/h excess-speed margin may be tested as an initial prototype setting, not treated as a legally approved tolerance or proven measurement accuracy. Tune the margin and persistence duration against reference speed measurements and controlled tests.

Hardware Components

G.U.A.R.D.I.A.N. combines existing computing equipment with low-cost external electronics to demonstrate a portable driver monitoring and alert system. The current prototype uses a laptop for computer vision and a dedicated microcontroller for physical indicators, with a future upgrade path to standalone edge computing.

03 / Hardware Communication Flow

Hybrid Architecture
Stage 01 / Input

Camera + GPS

The USB webcam supplies video frames. The GPS receiver supplies position, speed, and fix information through its supported USB or serial interface.

Stage 02 / Processing

Laptop + Python

The existing computer-vision pipeline processes video. GPS data and other valid inputs feed the risk engine, which determines monitoring states and warning events.

Stage 03 / Output

ESP32 + Display

USB serial carries status commands to the ESP32. The microcontroller updates LEDs and the OLED and activates the appropriate buzzer output.

Network communication: The laptop's existing Wi-Fi connection can transmit authenticated event summaries to the project's backend. A phone hotspot is sufficient for an internet-connected demonstration. Local detection and alerts should continue when network connectivity is unavailable.
