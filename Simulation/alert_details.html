01 / System Overview

What this subsystem is responsible for

The embedded subsystem is intended to provide a lightweight, local source of vehicle telemetry and immediate driver-facing warnings. It is a separate component from the Python computer-vision pipeline; later integration can combine their outputs into a broader risk-assessment system.

Implemented in simulation

GPS telemetry

Receives NMEA sentences from a simulated GPS module and parses latitude, longitude, and speed using TinyGPSPlus.

Implemented in simulation

Local status display

Displays GPS validity, speed in km/h, approximate coordinates, and the current speed status on a 128 × 64 SSD1306 OLED.

Implemented in simulation

Local alert outputs

Uses three LEDs to distinguish normal, caution, and high-speed states, with a pulsing buzzer for the high-speed state.

Implemented in firmware

State-transition logging

Prints a safety event when the state changes, including GPS loss, normal operation, caution, or high-speed alert.

Basic handling added

GPS freshness check

Checks whether GPS location and speed data are valid and recent. When data are unavailable or stale, speed-based LED and buzzer outputs are disabled.

Planned

Button & persistent logs

A physical push button has been obtained. Its wiring and acknowledgement behavior are not yet implemented; persistent event storage is also pending.

Scope note: current results are from a Wokwi simulation with generated GPS data. The subsystem has not yet been validated with a physical GPS receiver mounted on a moving vehicle.
02 / Data Flow

From GPS sentence to local alert

The current firmware follows a straightforward loop: receive serial data, parse it, check freshness, evaluate the speed threshold, then refresh the display and outputs.

01 · GPS moduleProduces NMEA sentences containing location and speed fields.
02 · UART2ESP32 receives GPS TX on GPIO 16 at 9600 baud.
03 · TinyGPSPlusParses incoming characters and exposes location, speed, validity, and age.
04 · State evaluationFreshness check and demonstration speed thresholds select the state.
05 · Local outputsOLED, LEDs, buzzer, and Serial Monitor communicate the current state.

03 / Implementation

What has been implemented so far

ESP32 firmware foundation

Configured serial diagnostics, GPIO outputs, I²C on GPIO 21/22, and SSD1306 initialization at I²C address 0x3C.

GPS UART integration

Configured Serial2.begin(9600, SERIAL_8N1, 16, 17). The GPS chip's TX connects to GPIO 16, the ESP32 receive pin. GPS RX is currently unused.

GPS parsing and diagnostics

Added TinyGPSPlus parsing for latitude, longitude, and speed. Serial diagnostics show processed character counts, valid sentences, and failed checksums.

GPS-driven speed state

Removed the old rotating synthetic-speed sequence from the active alert path. The displayed speed and alert state now use parsed GPS speed when the data pass the current validity/freshness checks.

Alert state transitions

Added event messages for GPS SIGNAL LOST, NORMAL, CAUTION, and HIGH SPEED. Events are currently printed to the Serial Monitor only.

Core firmware pattern

Illustrative excerpts from the current implementation. The complete sketch remains in sketch.ino in the Wokwi project.

GPS UART + parser
Serial2.begin(9600, SERIAL_8N1, 16, 17);

while (Serial2.available() > 0) {
  char incoming = Serial2.read();
  gps.encode(incoming);
}
GPS validity and speed thresholds
constexpr float CAUTION_SPEED = 60.0;
constexpr float HIGH_SPEED = 80.0;
constexpr unsigned long GPS_TIMEOUT_MS = 3000;

// Speed-based outputs are allowed only when GPS data
// are valid and recent.
if (!gpsDataFresh()) {
  digitalWrite(PIN_RED, LOW);
  digitalWrite(PIN_YELLOW, LOW);
  digitalWrite(PIN_GREEN, LOW);
  digitalWrite(PIN_BUZZER, LOW);
  return;
}
Threshold disclaimer: 60 km/h and 80 km/h are provisional demonstration thresholds in the current firmware. They are not road-specific legal limits or validated safety thresholds. A production system would need route-aware speed limits, sensor validation, and testing.
04 / Alert Logic

How the current alert states work

The firmware evaluates GPS speed against two configurable thresholds. The outputs are mutually exclusive in valid-data states.

Normal

Below 60 km/h. Green LED on; buzzer off.

Caution

60 to below 80 km/h. Yellow LED on; buzzer off.

High speed

80 km/h or above. Red LED on; buzzer pulses.

GPS unavailable

Speed-based LEDs and buzzer turn off; OLED shows GPS signal loss.

State transition logging

The firmware compares the current state with the previous state. It prints a safety event only when the state changes, plus the measured speed when GPS data are considered fresh. This reduces repeated messages while the system remains in one state.

Example output observed in simulation
[0 s] SAFETY EVENT: GPS SIGNAL LOST
[1 s] SAFETY EVENT: NORMAL
Measured speed: 17.96 km/h

--- GPS STATUS ---
GPS speed: 17.96 km/h
Latitude: -23.466333
Longitude: -51.840133
Valid sentences: 5
Failed checksums: 0

The values above are an example captured during the Wokwi simulation, not a fixed output or real-world trip record.

05 / Testing & Validation

Verified so far

  • ESP32 firmware compiles and starts in Wokwi.
  • OLED initializes and displays status, GPS speed, and coordinates.
  • Custom simulated GPS sends NMEA data over UART2.
  • TinyGPSPlus parses coordinates and speed (approximately 17.96 km/h in the observed run).
  • Serial diagnostics show increasing character and valid-sentence counts with zero failed checksums in the observed sample.
  • Green normal-state output has been observed at the simulated GPS speed.
  • Yellow caution LED was manually tested by temporarily lowering the threshold.
  • State-transition messages for initial GPS loss and subsequent normal state were observed.
  • High-speed LED and pulsing buzzer need a documented end-to-end test using a controlled test threshold or simulator speed.
  • GPS signal loss after a previously valid fix needs a dedicated test; the current simulator continuously transmits data.
  • Physical NEO-M8N, button, power behavior, and vehicle installation have not been validated.
Interpretation: a clean checksum count supports successful NMEA parsing, but it does not prove GPS accuracy, road-speed accuracy, or safety performance. Wokwi is a functional prototype environment, not a substitute for hardware and field testing.

07 / Current Limitations

What this prototype does not claim yet

  • It does not yet read OBD-II vehicle speed, engine data, or vehicle bus telemetry.
  • It does not yet save safety events to persistent storage or transmit them to a cloud backend.
  • The push button is not yet wired or implemented in firmware.
  • The current speed thresholds are examples and are not route-specific.
  • GPS-derived speed can be noisy or unavailable, especially during poor reception; a production implementation needs explicit validation and recovery behavior.
  • The embedded subsystem is not yet connected to the computer-vision pipeline or the web dashboard.
  • This prototype has not been safety-certified and must not be used as the sole basis for real-world driving decisions.
